# Hana 远程访问 · 技术文档（交接版）

对应代码：仓库内 `hana-remote-access/`（安装态与源码逐文件一致）
宿主：HanaAgent 1.0.6-beta，Windows；数据面 Node ≥ 22。
历史沿革：先做独立网关形态（同一份 `gateway/gw.mjs` 由用户进程直接托管），再内化为 v2 应用。

## 1. 架构一句话

**两条腿 + 一个不受沙箱约束的托管进程。** 浏览器走公网进网关，网关再以「LAN 值 Host」把请求转给只监听回环的 HanaAgent；网关自己需要宿主特权时用「回环 Host + owner token」这第二条腿。

```
手机/PC 浏览器
   │ https://<publicBaseUrl>            （NAS 反代终止 TLS）
   ▼
网关进程  listen 0.0.0.0:<port=19388>   ← 由应用经 ctx.runtime 托管（profile:local-machine, network:external）
   ├─ 浏览器腿：Host = frontHost()（LAN 地址或 publicHost）→ 宿主判为 connectionKind:"lan"
   └─ 特权腿：Host = 127.0.0.1 + Authorization: Bearer <owner token> → connectionKind:"local"
   ▼
HanaAgent  127.0.0.1:31787（HTTP；TLS 由 NAS 侧终止）
```

## 3. 关键实现点（改代码前先看这些）

1. **就绪标记**：`gateway/gw.mjs` 在 listen 回调里打印独占一行 `HANA_REMOTE_ACCESS_READY`；宿主只在 stdout 命中该串后才认为 `service.state === "ready"`。删掉它就再也没有就绪判定。
2. **App 主进程没有网络**：AppHost 子进程跑在 Node Permission Model 下，不开 `--allow-net`，也不能读安装/数据目录之外的文件。因此
   - 端口探测、`server-info.json` 读取、日志尾部**全部由网关服务自己出**（`/api/pair/diag`、`/api/pair/logs`）；
   - 应用路由访问服务只能用 `ctx.runtime.fetch(runtimeId, path, init)`（宿主固定 origin 为 `127.0.0.1:<port>`）。
3. **受管运行时 API 形状**：`start(input) → HanaPluginRuntimeInfoV2`、`stop(runtimeId)`（**位置参数**）、`fetch(runtimeId, path, init) → Response`（要 `await res.text()`）、`list()` 里用 `row.service.id === "gateway"` 且 `service.state === "ready"` 判定。`findService()` 会过滤掉终态记录，别拿终态当服务。
4. **变量遮蔽**：`gw.mjs` 路由器里 `const path = url.pathname` 遮蔽了模块级 `path`。任何新增端点都要用模块作用域常量（如 `requestLogFile`），否则静默失败（历史上日志端点就这么空转过）。
5. **日志 tee 要绑原始句柄**：`console.log = (...a) => { originalLog(...a); tee(...) }`。直接在被覆盖的 `console.log` 里自调用会 `RangeError` 让进程一启动就崩。
6. **cookie 策略**：上游 `Set-Cookie` 透传（宿主的 `/api/web-auth/session` 只认 cookie），仅当浏览器侧确为 https（`x-forwarded-proto: https`）时补 `Secure`。`Authorization` 在升级 WS 时**不**转发，只转浏览器自己的 cookie。
7. **WS 超时**：`socket.setTimeout()` 是**空闲**计时器，会把安静但健康的隧道反复掐死。现在只在握手阶段计时，收到 101 首个字节即清除。
8. **owner token 生命周期**：1.0.6 在宿主关机时 `unlink ~/.hanako/server-info.json`，启动才重写。所以网关重启前必须宿主在跑；`/healthz` 与配对前都会重读该文件（`waitForUpstream`）。
9. **名册**：`devices.json` 是 `{deviceId:{createdAt,lastSeenAt,userAgent,credentialId}}`，0600 + 临时文件 rename。取消配对时 await 吊销宿主凭证（早期是 fire-and-forget，进程退出会留下活的死钥匙）。
10. **配对即登录**：`/api/pair/accept` 顺手用特权腿铸钥匙 + `POST /api/web-auth/login {credential}` 换会话 cookie，一并下发。铸钥匙失败只降级为「需手动登录一次」，不影响配对本身。

## 6. 与宿主的关系（重要约束，别踩）

- 宿主的访问控制面 `/api/access/*`、`/api/devices/*` 锁本机（`local_only_route` / `local_owner_required`）→ 远程设备只能聊天/读文件/用应用本体，改配对要回本机。
- 宿主不认 `X-Forwarded-*`；Host 归一化会剥掉一个尾随 `:port`。所以两条腿必须给**不同 Host**。
- 设备凭证会话要求 `connectionKind:"lan"`；owner token 要求 `"local"`。
- 宿主的 `/mobile/` 缺陷定位（1.0.6 实测，行号为下发构建内偏移）：
  `assets/MobileApp-DI126sxl.js:6546` 用裸 `d.setState({activeServerConnection:o,…})`，而唯一写 `inputDraftVerified` 的 `YR()`（`assets/index-euu4IScK.js:217922`）只在 `setActiveServerConnection`/`applyServerConnectionState`（同文件 228336 一带）里被调用；`verified` 判定 `inputDraftVerified===!0 && vC().verified`（`216875`）；建会话 `POST /api/sessions/new-detached` 前有一道 `if(!verified) throw`（`assets/schedule-draft-BTcZZHVL.js:221931`）。`/pad/` 与桌面壳走 `App-DHx3f80o.js`（5 处 `applyServerConnectionState`）→ 不受影响。

## 7. 构建 / 安装 / 验证

```bash
TOOLS="$HOME/.hanako/artifacts/server/<当前运行版本>/scripts"
cd <本仓库的上一级目录>   # 下面所有路径都相对它

# 必须从 git archive 的干净导出打包，不要在仓库根上直接 --dir：
# 打包器把 --dir 里的一切原样塞进 zip，仓库根上跑会把 .git/（config、hooks、对象库）一起打进去
# —— 实测从 2.8 MB / 379 个文件变成 5.5 MB / 791 个文件。
# 另外两个硬约束：--dir 的目录名必须等于 manifest.id（否则报 id ... does not match its directory name），
# 且别用 /tmp（Git Bash 的 /tmp 与 node 解释的不是同一个地方）。
STAGE=build/pack-stage
rm -rf "$STAGE" && mkdir -p "$STAGE/hana-remote-access"
git -C hana-remote-access archive --format=tar HEAD | tar -x -C "$STAGE/hana-remote-access"
node "$TOOLS/extension-pack.mjs" --kind app --dir "$STAGE/hana-remote-access" --publisher TomDarkWay --out dist
node "$TOOLS/validate-app.mjs" --archive dist/app-hana-remote-access-1.0.1.zip --json     # 期望 errors=0
sha256sum dist/app-hana-remote-access-1.0.1.zip    # 必须等于市场 approvals.json 里登记的哈希

# 装载后的可复现自检（在本仓库内，只读）
#   设置页「一键体检」= GET /api/apps/hana-remote-access/routes/doctor，7 项：
#   server-info / 网关监听 / 宿主可达 / lan 模式 / 公网地址 / 允许 Host / 已配对设备；
#   它转调网关的回环端点 /api/pair/diag（只有回环来源能访问）。
# 安装与端到端穿透验证脚本在作者工作区，未随包发布：
#   install-app.mjs（local 源安装 + confirm）、app-check.mjs（写配置 + 轮询 + 体检 + 出码）、
#   gw-through-app.mjs（accept→sessions→ws-ticket→WS 101→自动清理）
```

改代码后要**刷新安装目录**（打包器只产 zip，不会替你装）：删 `~/.hanako/apps/hana-remote-access` → 解压新 zip → `POST /api/extensions/app%3Ahana-remote-access/reload`。
注意：能力清单变化会走确认卡（`reload` 返回 `awaiting_confirmation`）—— **不要替用户 API 确认**；缩小能力则静默生效。

## 8. 排障速查

| 现象 | 先看 | 常见原因 |
| --- | --- | --- |
| status `running:false` | `service.state`、`lastStartError`、`<dataDir>/gateway.log` | 端口被占（旧独立网关/计划任务）、就绪标记没打印、进程崩（日志 tee） |
| 手机「连接尚未确认」+ 无限重连 | 网关日志有无 `[ws] /ws → 101` | WS 空闲超时（历史缺陷）、`/api/ws-ticket` 非 200 |
| 403 `invalid_transport` / `loopback_host_mismatch` | 浏览器腿的 Host 是否在 `trustedHosts`、宿主是否 lan 模式 | 两腿 Host 混用、宿主停在 loopback |
| 扫码后仍要登录 | `POST /api/web-auth/login` 是否 200、`/healthz` 的 `ownerTokenLoaded` | 宿主没在跑（server-info.json 被删）、铸钥匙失败降级 |
| 设置页空白 | 宿主桥握手是否完成（现在失败会显示红字而非白页） | iframe 未拿到 `appSurfaceSession` |
| 配对后旧设备掉线 | `devices.json` 时间戳 | 历史上是名册上限静默淘汰（已改为拒绝）；确认没被自检脚本清掉 |

## 10. 安全说明（如实）

- owner token 只存在于网关进程内存，从不下发浏览器；特权腿只用于铸钥匙/换会话/吊销这几次回环调用。
- 网关不信任 `X-Forwarded-For`；`X-Forwarded-Proto` 只用来决定自家 cookie 的 `Secure`。
- 配对令牌一次性、限时（默认 10 分钟）、`/api/pair/cancel` 可作废；配对 cookie 30 天。
- `profile:"local-machine"` 意味着网关进程以当前用户权限运行、**没有文件系统隔离**：它能读 `server-info.json`、能监听任意端口。这是功能必需，也是安装确认卡必须让用户看清的一点。
- 转发 zip 前检查个人信息：
  解包后对包内文本跑一次 grep，模式用你自己的域名、内网网段、用户名，以及宿主凭证与 owner 前缀的字面量拼出来（这些字面量本身不要写进文档，否则检查命令自己就成了命中项）。
